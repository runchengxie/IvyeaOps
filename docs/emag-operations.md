# eMAG 巡检工作台

管理员可通过侧栏“全部工具 → eMAG 巡检”或 `/emag` 进入。先用 [只读 CLI](emag-readonly.md)采集商品，再在页面“重新读取已采集资料”。这个按钮只重读本地证据，不调用 eMAG。

页面选择配置数据目录中已有的 RO 商品快照店铺，显示采集时间、来源、异常商品和数据限制。有库存的价格无效记录优先显示；订单、退款、费用和独立 FBE 明细仍显示为未采集。

## 人工处理记录

待核实 → 已拟方案 → 已批准 → 已执行（人工记录）→ 已复查。每步必须填写说明，前端和后端都不会因此修改真实店铺。

- 方案说明应包含字段、旧值、新值和理由；批准是管理员记录的人工决定。
- “已执行”用于记录已经在卖家后台人工完成的操作，不是平台执行成功的回执。
- 执行后重新运行采集命令，再从历史记录选择“用当前快照记录复查”。服务端要求指定已查看的新版本，并记录原异常在该版本是否仍存在；“未观察到”不等于所有经营风险都消失。
- 新快照的异常从待核实开始，不继承旧版本的批准或执行状态。旧版本仍可在历史中识别商品、异常类型和说明。页面只展示最近100条处理记录。
- 刷新会清空未保存的表单。记录版本冲突或证据已过期时，服务端拒绝保存并要求重新读取。

## 技术边界

管理员 REST 接口：`GET /api/emag/stores`、`GET /api/emag/stores/{store_id}`、`POST /api/emag/stores/{store_id}/issues/{issue_id}`。状态更新携带源 `snapshot_id`、当前 `revision`、下一 `state` 和 `note`；复查另带 `review_snapshot_id`。操作者取自已认证用户，客户端不能指定。未新增平台写接口或自动审批机制。

处理记录存入配置 data 目录的 `emag-operations.sqlite3`；快照保持不可变。发布锁在 `store-artifacts/publication-lock.sqlite3`，协调跨进程的快照导入和状态提交。不要绕过导入服务手工修改快照目录。

本阶段不删除原有 Amazon 模块、不改变默认首页、不增加模型或调度器。eMAG 专用入口先验证日常运营闭环，再按实际使用精简其他板块。
